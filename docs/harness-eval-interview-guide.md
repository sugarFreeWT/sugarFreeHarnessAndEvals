# HarnessAndEval 项目理解与面试讲解指南

> 本文围绕项目的四个简历亮点展开，帮助你理解 Harness 和 Eval 的核心思想，并在面试中按照“问题—设计—实现—结果—反思”的方式讲清项目。

## 一、先用一句话讲清项目

这是一个面向大模型 Agent 的测试与评测框架：我先用 Harness 把模型、Prompt、工具调用和 Agent 执行过程变成可控制、可观测、可回放的数据，再用 Eval 评估正确性、稳定性和执行效率，最后通过发布门禁和负面案例回流形成持续质量闭环。

项目当前将 JD 中的 Skills 类能力映射为“工具与插件能力”：测试重点不是 Skill 文案本身，而是 Agent 是否选择了正确能力、是否传入正确参数、能力执行失败后能否恢复，以及整条调用链是否符合预期。

## 二、Harness 和 Eval 分别解决什么问题

### 1. Harness：让 Agent 能被可靠地运行和观察

Harness 可以理解为 Agent 的运行底座。它负责组织一次任务从输入到结束的全过程：

1. 接收用户 Prompt，并组合可选的 system prompt；
2. 将消息历史和工具定义发送给模型；
3. 解析模型回答或工具调用请求；
4. 校验工具名称和参数；
5. 执行工具，将结果重新放回上下文；
6. 重复循环，直到模型直接回答、发生错误、超时或达到最大步数；
7. 记录每个关键事件、Token、步骤数、工具调用数和终止原因。

项目中的核心 Agent Loop 位于 src/sugarfree/core/agent.py。它并不只返回最终答案，还会记录 model.requested、model.responded、tool.requested、tool.completed、tool.failed、run.completed 等事件。

这层设计的重要性在于：Agent 失败通常不只是“答案错了”，还可能是选错工具、参数不合法、工具异常后不会恢复、陷入循环、越权访问文件或者虽然答案正确但调用成本明显增加。没有 Harness 的结构化证据，就很难判断问题发生在哪一层。

### 2. Eval：定义什么叫“好”，并自动判断是否退化

Eval 是建立在 Harness 运行结果之上的质量判断系统。它包含四个关键部分：

- 评测标准：明确要检查哪些质量维度；
- 评测集：用具体 case 表达输入、场景和预期；
- 评估器：把运行结果转换成通过/失败及诊断信息；
- 质量流程：通过基准比较、发布门禁和失败回流持续维护质量。

可以用一句话记忆二者关系：

> Harness 负责产生可信的过程证据，Eval 负责根据标准判断这些证据是否合格。

## 三、项目的完整质量链路

    Eval Case
       │  Prompt、预置环境、期望结果
       ▼
    Eval Runner
       │
       ▼
    Agent Harness ──► Model
       │               │
       │◄──回答/调用────┘
       ▼
    Tool / Skills 类能力
       │
       ▼
    Events + Messages + Workspace Changes
       │
       ▼
    Scorers
       │
       ├──► report.json / JSONL 轨迹
       │
       ├──► Benchmark 多轮对比
       │
       ├──► Release Gate 发布门禁
       │
       └──► Failure Inbox 负面案例回流

这条链路对应了测试开发的基本思想：先让系统可测，再定义预期，之后自动判定、阻断回归，并把线上或真实模型失败重新沉淀为测试资产。

## 四、亮点一：建设评测标准和分层评测集

### 1. 要解决的问题

只看最终答案无法完整评价 Agent。例如模型最后给出了“42”，但它可能调用了错误工具、使用了不合法参数、重试了很多次，或者访问了不该访问的文件。另一方面，真实模型输出存在随机性，如果所有回归都依赖在线 API，测试会慢、成本高且结果不稳定。

### 2. 我的设计

我把质量标准拆成四层：

| 评测对象 | 核心问题 | 项目中的检查方式 |
| --- | --- | --- |
| 模型输出 | 最终答案和结束状态是否正确 | answer_contains、termination_reason |
| Prompt 遵循 | 是否遵守简洁回答、不调用非必要工具等要求 | 答案断言、forbidden_events、max_tool_calls |
| Skills/工具 | 是否选择正确能力、参数是否正确、失败后能否恢复 | required_tools、required_tool_calls、tool.failed/tool.completed |
| Agent 链路 | 步骤、终止、事件和工作区副作用是否符合预期 | max_steps、required_events、workspace_changes |

评测集采用两层结构：

- 确定性离线集：使用 ScriptedModel 预置模型响应，重点验证 Harness 架构和链路行为，不调用外部 API；
- 真实模型集：使用 DeepSeek 检查真实模型的 Prompt 遵循、工具选择和多步行为。

evals/agent-regression.json 当前包含 23 条确定性回归用例，覆盖：

- 直接回答与非必要工具抑制；
- 单工具、多工具串联和并行工具调用；
- 缺少参数、额外参数、未知工具和工具执行错误后的恢复；
- 模型错误、最大步数和执行边界；
- 文件新增、修改、无副作用读取和路径穿越防护。

用例通过 core、tool、recovery、workspace、security、negative 等标签组织，使报告既能输出总通过率，也能输出某一能力维度的通过率。

### 3. 为什么同时需要离线和真实评测

离线评测解决“可重复”：相同输入一定得到相同模型脚本，适合 CI 和架构回归。

真实评测解决“有效性”：验证真实模型是否真的能够理解 Prompt、选择工具并完成任务。

二者不是替代关系。只做真实评测会有随机性和成本问题；只做脚本评测只能证明 Harness 按设计运行，不能证明真实模型表现良好。

### 4. 面试时可以这样讲

“我没有只用最终答案作为测试标准，而是把评测对象拆成模型输出、Prompt 遵循、Skills 类工具调用和 Agent 链路四层。离线 Regression 用 ScriptedModel 保证 CI 稳定，真实 DeepSeek Smoke 用例验证实际模型行为。最终形成了 23 条确定性回归用例和 10 条真实模型用例，既保证可重复性，也保留真实有效性。”

## 五、亮点二：实现可扩展评估器和轨迹回放

### 1. 要解决的问题

Agent 的一次运行会产生多种证据：答案、工具调用、参数、事件、文件变化、步骤数和终止原因。如果把所有断言都硬编码在 Runner 中，后续新增质量维度会导致代码耦合，失败报告也难以定位。

### 2. 我的设计

项目把每种判断封装为独立 Scorer，位于 src/sugarfree/evals/scorers.py，包括：

- TerminationScorer：终止原因是否符合预期；
- AnswerContainsScorer：答案是否包含关键内容；
- RequiredToolsScorer：必需工具是否被调用；
- RequiredToolCallsScorer：工具名称和参数组合是否正确；
- MaxToolCallsScorer：工具调用是否超出上限；
- MaxStepsScorer：执行步骤是否超出上限；
- WorkspaceChangesScorer：文件新增、修改、删除是否符合预期；
- EventScorer：必需事件是否出现、禁止事件是否缺失。

每个 Scorer 返回结构化 Score，包含评分器名称、通过状态和诊断详情。Runner 汇总为 report.json，并按标签计算通过率。

Harness 同时将事件追加写入每个 case 的 JSONL 轨迹。ReplayModel 可以读取原始轨迹中的模型响应，工具仍重新执行，并严格比较每一步模型请求。这样可以验证：

- Harness 改动后，请求消息或工具 Schema 是否发生意外变化；
- 工具执行和事件序列是否仍可复现；
- 不再调用真实模型时，是否仍能复盘原始执行链。

### 3. 一个具体例子

missing_argument_recovery 用例先让模型调用 calculator，但不提供 expression 参数。Harness 的参数校验应产生 tool.failed；随后模型使用正确参数再次调用，产生 tool.completed，并最终正常结束。

这个 case 不只是验证“答案对不对”，而是在验证一条恢复链：

    非法调用 → 参数校验失败 → 错误返回上下文
             → 模型修正参数 → 工具成功 → Agent 完成

如果最终答案正确，但没有出现预期的失败和恢复事件，用例仍然可以判定链路不符合设计。

### 4. 面试时可以这样讲

“评估器采用可插拔 Scorer 设计，每个评分器只负责一个质量维度，新增规则不需要修改 Agent Loop。除了最终答案，我还校验终止原因、工具和参数、步骤数、事件以及工作区副作用。每个 case 都保存 JSONL 轨迹，严格回放会逐步比较模型请求，使 Harness 的结构变化也能被检测出来。”

## 六、亮点三：将评测结果转化为发布门禁

### 1. 要解决的问题

有评测报告不代表它能真正保护发布。如果测试失败后仍可继续合并，或者只看总通过率，就可能出现核心场景丢失、某一能力整体退化、旧用例被删除掩盖失败等问题。

### 2. 我的设计

发布策略位于 gates/offline-release.json，门禁同时检查：

- 用例总数不少于 23；
- 整体通过率达到 100%；
- 指定核心 case 必须存在且通过；
- core、tool、recovery、workspace、security、negative 等关键标签通过率达到 100%；
- 必须存在严格回放报告，且回放和当前报告逐 case 一致；
- 版本化基线中的用例不能被静默删除；
- 不允许出现新增失败；
- 平均步骤数和平均工具调用数的增长不能超过阈值。

门禁失败时仍会生成可诊断的 gate report，并返回非零进程码，使 GitHub Actions 直接失败。CI 流程依次执行源码编译、单元与集成测试、架构 Smoke、Regression、严格回放、Benchmark 和 Release Gate。

这里的关键不是“检查越多越好”，而是检查不同类型的风险：

- 通过率检查功能正确性；
- required case 和标签阈值检查覆盖面；
- 基线比较检查新增回归和用例删减；
- 步骤数、工具调用数检查效率退化；
- 严格回放检查执行链结构是否改变。

耗时和 Token 会进入 Benchmark，但没有作为严格离线门禁的唯一依据，因为网络延迟和真实模型 Token 存在自然波动。门禁优先使用更稳定、可解释的指标。

### 3. 项目结果

当前完整离线 CI 验证结果为：

- 67 项测试通过，1 项跳过；
- Architecture Smoke：10/10；
- Architecture Replay：10/10；
- Agent Regression：23/23；
- Regression Replay：23/23；
- Release Gate：20/20 检查通过。

### 4. 面试时可以这样讲

“我把 Eval 从一份展示报告变成了真正的发布约束。门禁不仅看总通过率，还检查关键标签、核心用例、回放一致性、基线用例删除、新增失败以及步骤和工具调用退化。任一检查失败都会输出诊断报告并让 CI 返回非零状态，从流程上阻止有回归的版本发布。”

## 七、亮点四：建立负面案例回流闭环

### 1. 要解决的问题

评测集如果长期只靠人工预想，会漏掉真实模型中出现的新问题；但如果把每次失败自动写入正式评测集，又会把网络故障、API 鉴权问题、模型偶发波动、重复问题甚至敏感信息当成质量标准。

### 2. 我的设计

负面案例采用以下状态流转：

    candidate → approved → promoted → resolved
             ↘ rejected

具体流程为：

1. Collect：从失败 report 中提取失败 case；
2. Deduplicate：根据评测套件、原 case、失败评分器和终止原因计算 SHA-256 指纹；
3. Review：人工判断它是产品/Agent 行为问题，还是环境、鉴权或偶发问题；
4. Author：对有效问题手工编写确定性 Regression case；
5. Promote：把已批准失败与新 Regression case 关联；
6. Reconcile：只有关联 case 在回归报告中通过，问题才变为 resolved。

同一报告重复收集不会重复计数；不同运行中出现相同失败会合并，并增加 occurrence_count。Inbox 还保留首次和最近出现时间、来源报告、轨迹路径、失败原因及审核记录。

### 3. 为什么不能自动把失败 Prompt 加入回归集

正式回归用例必须具有稳定、明确、可解释的预期。真实失败可能来自：

- API Key 失效或网络超时；
- 模型概率波动；
- Prompt 本身描述不清；
- 评估器误判；
- 真正的 Agent 或工具链缺陷。

因此项目只自动收集证据，不自动制定测试标准。人工审核负责判断问题性质，并将真实失败改写成确定性 case。这体现了测试资产治理，而不是简单的数据堆积。

### 4. 安全处理

写入 Inbox 前统一对 sk-、Bearer、api_key、token、secret、password 等凭据脱敏。项目曾遇到供应商 401 响应中携带掩码 Key 后缀的情况，因此又补充了该类格式的脱敏规则和测试。

这是一个很适合面试展开的真实案例：

- 现象：真实评测出现 401；
- 排查：确认失败来自 API 鉴权，而不是 Agent 行为；
- 处置：候选失败进入 Inbox 后被人工 rejected，没有污染 Regression；
- 改进：发现错误文本可能包含凭据线索，补充统一脱敏模块和测试；
- 验证：配置有效 Key 后，三轮真实 DeepSeek 评测均为 10/10。

### 5. 面试时可以这样讲

“我没有让真实失败直接污染正式评测集，而是设计了候选、审核、提升和关闭的状态机。相同失败用稳定指纹去重，人工确认后再手工写成确定性 Regression case；只有该 case 回归通过才关闭问题。这样既能从真实失败中持续扩充测试资产，又能过滤环境故障、偶发噪声和敏感信息。”

## 八、三种长度的面试表达

### 1. 30 秒版本

“我做了一个 Agent Harness 与 Eval 项目。Harness 负责模型调用、工具执行、超时、权限和事件轨迹，让 Agent 的执行过程可观测、可回放；Eval 侧建设了 23 条确定性回归用例和多维评估器，并把通过率、核心能力、回放一致性和链路效率接入发布门禁。对于真实模型失败，我又设计了指纹去重、人工审核、回归用例关联和修复关闭的负面案例闭环。最终离线 Regression 23/23、门禁20/20通过，DeepSeek 三轮共30次真实用例保持100%通过。”

### 2. 2 分钟版本

“这个项目的背景是 Agent 不像普通接口那样只有输入和输出，它中间还会选择工具、生成参数、多步执行并处理异常，所以只判断最终答案不足以发现链路问题。

我先搭建了一个与模型厂商解耦的 Harness，通过统一 Model 和 Tool 接口实现 Agent Loop，同时记录模型请求、工具调用、异常、终止原因、Token 和工作区变化。然后在这个基础上设计 Eval，把质量拆成模型输出、Prompt 遵循、Skills 类工具调用和 Agent 链路四个层面。

评测集分为确定性离线集和真实模型集。离线集使用 ScriptedModel，目前有23条 Regression，可以稳定接入 CI；真实集使用 DeepSeek 验证实际模型行为。评估器不只看答案，还检查工具与参数、最大步骤、关键事件和文件副作用，并用 JSONL 轨迹做严格离线回放。

为了让评测真正影响发布，我设计了20项门禁检查，包括总通过率、关键标签、核心用例、回放一致性、基线删减、新增失败和步骤数、工具调用数退化。真实失败则先进入 Inbox，用指纹去重和人工审核，再关联手工编写的 Regression case，回归通过后才关闭。

最终完整离线链路中 Regression 23/23、门禁20/20通过；DeepSeek连续三轮共30次真实用例全部通过。这个项目让我理解了 Agent 测试的重点不是只看回答，而是对完整决策和执行链建立可观测、可重复、可治理的质量体系。”

### 3. 一句话收尾

“这个项目最核心的价值，是把不稳定、难解释的 Agent 行为转化为可记录、可评分、可阻断、可持续回归的测试资产。”

## 九、面试高频追问与回答

### Q1：Eval 和普通单元测试有什么区别？

单元测试主要验证确定性代码单元；Agent Eval 面对的是模型输出和多步决策，除了正确性，还要评价工具选择、链路过程、成本和稳定性。本项目没有抛弃单元测试，而是让单元测试验证框架组件，让 Eval 验证 Agent 行为，两者共同进入 CI。

### Q2：为什么不用真实模型跑全部 CI？

真实模型存在费用、网络依赖、限流和概率波动，容易造成 CI 偶发失败。项目用 ScriptedModel 验证确定性架构和回归，用少量真实 Smoke 定期验证模型有效性。这样兼顾速度、成本、稳定性和真实性。

### Q3：最终答案正确，为什么还可能失败？

因为 Agent 的过程也是产品行为。例如调用了禁止工具、参数不安全、修改了不该修改的文件、用了过多步骤，或者错误恢复路径失效，这些都可能在最终答案正确时被掩盖。因此需要过程级 Scorer 和事件断言。

### Q4：如何测试 Prompt？

当前不是给 Prompt 打一个笼统分数，而是把 Prompt 要求转换成可执行断言。例如“不要调用非必要工具”对应 max_tool_calls=0 和禁止 tool.requested；“必须查询后计算”对应 required_tool_calls 和调用顺序；“回答必须包含关键信息”对应 answer_contains。这样比主观评价更稳定。

### Q5：如何评测 Skills？

当前项目没有实现独立的 Skill 文档运行时，而是把 Skills 类能力抽象为工具和插件。评测重点是能力是否被正确选择、参数是否正确、结果是否进入上下文、异常是否恢复。若后续接入真正的 Skill Runtime，可以沿用相同标准，再增加 Skill 版本、依赖和加载成功率等指标。

### Q6：为什么需要严格回放？

普通结果回放只能知道最后是否通过，严格回放还能发现请求消息、工具 Schema 或上下文拼接发生变化。它适合检测 Harness 重构引入的隐性行为差异，而且不需要再次调用真实模型。

### Q7：门禁阈值为什么这样设计？

当前评测集规模较小且属于核心离线回归，因此整体和关键标签要求100%通过；平均步骤和工具调用允许0.25的增长，避免轻微结构调整造成误报，同时可以阻止明显效率退化。真实耗时和Token波动较大，所以进入基准报告观察，而不是直接作为严格离线门禁。

### Q8：三轮100%通过能证明模型完全稳定吗？

不能。它只能说明在当前10条 Smoke、temperature=0和三轮样本下没有观察到失败。它是一次工程验证，不是统计意义上的完整稳定性证明。要进一步提高可信度，需要扩大 Prompt 变体、模型版本、运行轮数和场景覆盖，并计算失败率和置信区间。

### Q9：负面案例为什么一定要人工审核？

因为失败不等于产品缺陷。鉴权错误、网络超时、评估器误判和模型偶发波动都可能产生失败。人工审核负责分类和确定预期，防止把噪声固化为错误的回归标准。

### Q10：项目目前最大的不足是什么？

当前优势是测试链路完整，但评测内容仍偏小型、确定性和工具型场景。语义质量主要使用关键片段判断，还没有引入人工标注集、模型裁判一致性校准、统计显著性分析和大规模并发执行。下一阶段应优先增加真实业务任务、Prompt 变体和多模型对比，而不是继续堆框架功能。

## 十一、需要牢记的项目边界

面试时应主动保持表述准确：

- 项目是小型 Agent Harness 与 Eval 原型，不是生产级大规模平台；
- 当前 Skills 以工具和插件能力映射，不声称实现了完整 Skill Runtime；
- answer_contains 适合确定性任务，但不能覆盖复杂语义质量；
- 三轮100%是当前样本结果，不代表所有场景绝对稳定；
- Local Runner 是策略限制，不等于操作系统级安全沙箱；Docker Runner 才提供更强隔离边界；
- 负面回流流程已经实现，但这次真实评测没有行为失败，因此没有人为制造“已解决”的案例。

准确说明边界不会削弱项目，反而能体现你对测试有效性、数据可信度和工程风险的理解。

## 十二、最后的记忆框架

面试前只需记住五个词：

1. 可控：最大步数、超时、权限和工具边界；
2. 可观测：事件、消息、Token、文件变化和终止原因；
3. 可评估：用例、标签、Scorer 和报告；
4. 可阻断：基线、回放、阈值和 CI 门禁；
5. 可进化：真实失败收集、审核、回归化和关闭。

把这五点讲清楚，就能说明你做的不只是“调用一次大模型”，而是一套围绕 Agent 行为建立起来的测试与质量保障方法。
